## Project status

The full stack is live end-to-end: `backend/` (Pyomo optimization + a local-only FastAPI wrapper, not deployed anywhere), `supabase/` (cloud project `food-opt`, ref `fufzybvwbdgejnozrgoa`, schema + USDA snapshot + 23 sample recipes pushed to both local and cloud), and `frontend/` deployed to Vercel at **https://food-opt.vercel.app**. The full user flow — email/password login → save preference sliders → save nutrient targets → manage recipes → generate a meal plan (with shopping list) via the local backend API — has been verified by actually clicking through it in a real browser, both against production (the first three steps) and fully end-to-end against local (all five, since the plan-generation step needs the backend API running locally). See `especificaciones/03-tasks.md` for the bugs that surfaced doing that and how they were fixed. Bugs found this way get a GitHub issue and are closed via `Fixes #N` in the fixing commit — see [issue #1](https://github.com/leonidasf300/food_opt/issues/1) and [issue #2](https://github.com/leonidasf300/food_opt/issues/2).

Specs live under `especificaciones/` following the **SDD (Spec-Driven Development)** methodology — see [`especificaciones/README.md`](especificaciones/README.md) for the full phase breakdown and [`especificaciones/03-tasks.md`](especificaciones/03-tasks.md) for what's done vs. pending:

## Commands

### Backend (`backend/`)

```
cd backend
python -m venv .venv
.venv/Scripts/activate          # Windows; use .venv/bin/activate on macOS/Linux
pip install -r requirements.txt

python -m pytest -q             # run all tests
python -m pytest -q tests/test_model.py::test_solve_satisfies_nutrient_bounds_each_day  # single test

uvicorn food_opt.api:app --reload --port 8000   # local API, see backend/README.md
```

### Data layer (`supabase/`)

Requires Docker Desktop running.

```
npx supabase start              # boot the local stack (Postgres + Auth + REST + Studio, etc.)
npx supabase stop
npx supabase status             # local URLs/keys once running
npx supabase migration new <name>
npx supabase db reset           # reapply all migrations + seed from scratch, local only
```

Local ports are shifted to 58320-58329 (not the CLI's 54320-54329 default) — Windows dynamically reserves 54318-54417 for Hyper-V/WSL, which breaks binding in that range with a permissions error, not a port-in-use error. See `supabase/README.md` if this needs revisiting on another machine.

Cloud project is linked (`supabase/.temp/project-ref`). Commands that touch it need `SUPABASE_ACCESS_TOKEN` (personal token, not stored in the repo) and the DB password:

```
SUPABASE_ACCESS_TOKEN=... npx supabase db push --password '...'
SUPABASE_ACCESS_TOKEN=... npx supabase migration list --password '...'
```

Data import scripts (`supabase/scripts/`) are separate from migrations — they move rows, not schema — and have their own venv:

```
cd supabase/scripts
python -m venv .venv
.venv/Scripts/activate
pip install -r requirements.txt

USDA_API_KEY=... python import_usda.py   # needs a personal key: https://api.data.gov/signup/?key (DEMO_KEY's rate limit is unusably low)
python set_prices_co.py                  # run after import_usda.py -- needs the ingredient rows to already exist
python import_recipes.py                 # run after both of the above -- needs ingredients + prices
```

### Frontend (`frontend/`)

```
cd frontend
npm install
cp .env.local.example .env.local   # fill in NEXT_PUBLIC_SUPABASE_* from `npx supabase status` (repo root); NEXT_PUBLIC_BACKEND_API_URL defaults to http://localhost:8000

npm run dev                        # http://localhost:3000
npm run build                      # typecheck + production build
npm run lint
npm run test                       # vitest
```

`frontend/` has its own `CLAUDE.md`/`AGENTS.md`, auto-generated by `next dev` (regenerated on every dev run — this is expected, not stray output). It points agents at `node_modules/next/dist/docs/` since this Next.js version may differ from training data; read it before assuming Next.js API knowledge is current.

**Deployed at https://food-opt.vercel.app** (Vercel project `food-opt`, root directory `frontend/`). When re-importing or reconfiguring this project in Vercel, watch out: Vercel's monorepo auto-detection ("Services" preset) will try to deploy `backend/` (Python) as a second service alongside `frontend/`, since it sees a `requirements.txt`. It isn't one — `backend/` is a standalone optimization library with no HTTP entrypoint. If the Framework Preset ever ends up as "Other" instead of "Next.js" (check Project Settings → Build and Deployment), every route 404s even though the build succeeds; fix by explicitly setting Framework Preset to Next.js and redeploying.

**Testing login locally: use `http://localhost:3000`, never `http://127.0.0.1:3000`.** Next.js 16 dev mode blocks cross-origin requests to its own dev resources (HMR websocket, dev font endpoint) from any origin other than the one `next dev` reports. If an auth redirect (password-reset email link) lands on `127.0.0.1`, client-side hydration silently breaks on that page — no console error, the page just never finishes its auth check and stays blank forever. `supabase/config.toml`'s local `site_url` is set to `localhost` for this reason; don't "fix" it back to `127.0.0.1` to match whatever URL a browser happens to show.

## Architecture

Planned as an AI-assisted nutrition and grocery management platform with three pieces (per `especificaciones/01-specify.md`):

- **Frontend** (`frontend/`, Next.js App Router + TypeScript + Tailwind, deployed to Vercel): four pages.
  - `src/app/preferences/page.tsx` — sliders weighting the multi-objective optimization (cost, variety, prep time). Moving one slider redistributes the other two proportionally (`src/lib/preferences.ts::redistributeWeights`, unit-tested) so the three always sum to exactly 100 — matching the DB's `weights_sum_to_100` constraint by construction, not by validation after the fact. Auth is email + password (`supabase.auth.signUp` / `signInWithPassword`) — switched from the original magic-link flow because it's simpler for users (no email round-trip to log in). `enable_confirmations`/"Confirm email" is off on both local (`supabase/config.toml`) and cloud (Auth → Sign In / Providers dashboard toggle) so signup logs the user in immediately, no confirmation click needed. Password is stored by Supabase Auth itself (`auth.users`, hashed) — no separate credentials table. `src/app/forgot-password/page.tsx` and `src/app/reset-password/page.tsx` handle the reset flow via `resetPasswordForEmail`/`updateUser`, reusing the same Resend SMTP and the same explicit-redirect pattern as the old magic-link flow (see the local-login note above for why the target page must itself import the Supabase client). The Supabase client lives in `src/lib/supabase/client.ts`.
  - `src/app/targets/page.tsx` — daily min/max targets per nutrient (calories/protein_g/fat_g/carbs_g), upserted into `user_nutrient_targets`.
  - `src/app/recipes/page.tsx` — lists every recipe (the seed/global ones, `created_by is null`, are read-only here) and lets a signed-in user create/edit/delete their own recipes (name, prep time, ingredient lines with quantities in grams). No new migration needed: `recipes`/`recipe_ingredients` already had owner-scoped RLS + `GRANT`s for `authenticated` from the initial schema (`migrations/20260921140828_create_core_schema.sql`). Editing replaces all of a recipe's `recipe_ingredients` rows rather than diffing them — simpler, and cheap enough at recipe scale.
  - `src/app/plan/page.tsx` — reads the signed-in user's saved preferences + targets from Supabase, `POST`s them to the backend API (`NEXT_PUBLIC_BACKEND_API_URL`, local-only), and renders the returned day-by-day plan plus a "Lista de compras" table (quantity needed, units to buy rounded up to commercial purchase units, cost).
  - The full flow (login → preferences → targets → recipes CRUD → plan, including the shopping list) is verified working by hand in a real browser against local; login → preferences → save is additionally verified against production.
- **Data layer** (`supabase/`, Postgres via Supabase): schema for profiles/preferences/nutrient targets/ingredients/recipes, RLS enabled on every table (see `supabase/README.md` for the table-by-table breakdown and access rules). Cloud project `food-opt` (ref `fufzybvwbdgejnozrgoa`) exists with all 6 migrations pushed. Table access requires *both* RLS policies *and* the explicit `GRANT`s in `migrations/20260921161544_grant_table_privileges.sql` — RLS alone doesn't expose a table to the Data API. `migrations/20260921194319_create_profile_on_signup.sql` adds a trigger that creates a `profiles` row on every new `auth.users` signup (SECURITY DEFINER, since the new user has no session yet) — without it, any first-time save by a new user failed with a foreign key violation, since `preferences`/`user_nutrient_targets`/`recipes` all reference `profiles`. `migrations/20260921201908_create_recipe_totals_view.sql` adds a `recipe_totals` view (cost + nutrients per recipe, `security_invoker = true`) used by both the backend and the import scripts — its cost aggregation had a real fan-out bug (joining `ingredients` and `ingredient_nutrients` in one query multiplies the cost sum by however many nutrient rows exist per ingredient) that was only caught by diffing its output against an independently-computed script result. Auth email is sent via a custom SMTP (Resend) configured on the cloud project, because Supabase's built-in email service caps out at ~2-4/hour — nowhere near enough for real use; Resend's sender is still in test mode (`onboarding@resend.dev`, can only send to the Resend account's own verified email) until a custom domain gets verified. Verified end-to-end through the real Data API on both local and cloud (not just as the Postgres superuser): `anon` gets 401, `authenticated` can read `ingredients` but not write it (403), and can read/write its own `profiles`/`preferences`. `ingredients.purchase_unit_label/size/price` are nullable by design and now filled with **real Colombian retail prices** (`supabase/scripts/set_prices_co.py`), hand-curated from exito.com on 2026-09-22 (source: `especificaciones/00-constitution.md`) — not a live feed, no refresh schedule yet, so this will drift stale over time. An automated pricing source is still open — DANE SIPSA and DANE IPC were both investigated and ruled out (SIPSA only prices wholesale fresh produce, zero overlap with these 15 ingredients; IPC only publishes index variation, not absolute prices). See `especificaciones/00-constitution.md` for both findings. Applied against **both local and cloud**. `supabase/scripts/import_usda.py` (15 ingredients) and `import_recipes.py` (expanded from 8 to **23 sample recipes**, `seed_recipes.py`, still all built from the same 15 USDA ingredients — enough variety for roughly 4 weeks of plans without too much repetition) have been run for real against **both local and cloud**. Cloud requires the connection pooler, not the direct `db.<ref>.supabase.co` host (IPv6-only, fails to resolve on networks without IPv6) — and `prepare_threshold=None` on every `psycopg.connect()` call, or repeated statements against the pooler's transaction mode eventually fail with `DuplicatePreparedStatement`.
- **Optimization backend** (`backend/`, Python + Pyomo + HiGHS): solves a weighted multi-objective model — minimize cost, minimize prep time, maximize recipe variety — subject to per-day nutrient constraints. `food_opt/model.py` and `food_opt/shopping_list.py` stay pure, DB-free libraries; `food_opt/data.py` is the only module doing DB I/O (recipes from the `recipe_totals` view, recipe→ingredient breakdown from `recipe_ingredients`); `food_opt/api.py` is a local-only FastAPI wrapper (`POST /plans`) the frontend's `/plan` page calls.
  - `Recipe`, `NutrientTarget`, `Weights` (validates weights sum to 1.0) dataclasses; `build_model()` constructs the Pyomo `ConcreteModel`; `solve()` runs it through the `appsi_highs` solver interface.
  - Recipe selection is modeled as `x[recipe, day]` (integer servings, bounded) plus a `y[recipe]` binary variety indicator, linked to actual usage via two constraints (`usage_upper_bound`, `usage_lower_bound`) rather than a naive count — this avoids the solver getting "free" variety credit for unused recipes.
  - Cost ($), prep time (minutes) and variety (recipe count) are on different scales, so `build_model()` normalizes them via a payoff table before weighting: it silently solves each objective alone first (`_payoff_table()`) to get each one's ideal/nadir bounds, exposed on the returned model as `model.objective_bounds`. This means every `build_model()` call does 4 solves total (3 for the payoff table + the real one) — fine for interactive use, worth knowing if it ever needs to run in a hot loop.
  - `_normalized()`'s `maximize=True` branch (used for variety) had its sign inverted for a while — see [issue #2](https://github.com/leonidasf300/food_opt/issues/2): the fix is `(bounds.ideal - expr) / (bounds.ideal - bounds.nadir)`, not a naive mirror of the minimize branch, because `nadir - ideal` is negative for a maximized objective and the minimize branch's `span` can't be reused as-is. Covered by `test_higher_variety_weight_uses_more_distinct_recipes` — if you touch this function, that test (not just the boundedness/consistency ones) is the one that actually catches a regression here.
  - `food_opt/shopping_list.py::build_shopping_list()` sums each ingredient's quantity needed across every recipe/day in the solved plan, then rounds up to whole commercial purchase units (`math.ceil(quantity_needed / purchase_unit_size)`) and multiplies by `purchase_unit_price`; ingredients with no `purchase_unit_size`/`price` on file (still true for most beyond the 15 USDA-imported ones — see the Data layer note on placeholder pricing) report the raw quantity with `units_to_buy`/`cost` as `null` rather than guessing. `api.py::create_plan()` wires this in after the day-by-day loop, using total servings per recipe across the whole horizon (not per-day), and returns it as `PlanResponse.shopping_list`.
